# Archive export review

The previous JVM-capable executable treated the JAR's class records as
archive payloads during export. The ordinary JVM source query could already
read all three class definitions. The export now publishes those exact
source bytes from the same recovery engine.

The base `Edition.answer` retains multiplication by two and addition of
one. The release-17 definition retains multiplication by three and addition
of seven, at its separate physical coordinate. Its source obtains the
package path when that release is selected explicitly. In the unrestricted
inventory the two definitions stay independently readable. The inaccurate
base entry name does not change its binary package or member identity.
`Helper.square` multiplies the two original reads of the same wide
argument. Its resource method returns the exact original path.

The nested resource resolves to `j4/j1`. The resource query, path literal
xref, streaming extraction and directory output agree on that physical
entry and its available bytes. The xref establishes a matching literal;
the fixture has no runtime resource lookup. A secondary archive's
`a1/j0` entry remains distinct from the primary archive. Output aliases to
a project artifact are refused before publication.

The damaged class and CRC mismatch retain their original entry locations.
The damaged bytes cannot replace an existing extraction. Relocation of
the nonportable name retains its payload without altering the existing
sentinel. The folded manifest delivers its exact bytes even across a
UTF-8 sequence split by a physical line continuation. Runtime behavior of
the exported Java source was not independently executed in this fixture.
