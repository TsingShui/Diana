# Semantic review

The ordinary `methods --no-limit` and `get-class` commands were run on both assembled inputs with Diana 0.3.0. The original Kernel implementation and the new Gate expression perform the same ordered multiplication, XOR, subtraction and reverseBytes call. On both sides the calculation completes before the protected array read and division. Only the original Gate makes the intermediate Kernel call. The two old Gate/Kernel definitions and the single new Gate definition retain their actual member identities.

The old Gate catches ArithmeticException and returns -1 on division by zero. Its null array and invalid index fail during evaluation of the divisor and escape the method. In the new output the RuntimeException handler covers that read and the division, sending all three failures to the same return. Neither body evaluates the divisor a second time. The successful path divides the mixed value by the selected element once. These paths agree with the corresponding Java/Smali pair, including their intentional cross-version difference. The agreement was judged by reading, without execution on Android.

Direct inspection of the two code items locates the old helper sequence and the new inlined sequence at code-unit offset 0 in each method. Their first four opcode bytes in instruction order are 0xda, 0xdf, 0xd8 and 0x71. Their method pool indexes differ. The new arithmetic uses p0 in the larger caller frame. The array access follows the inlined move-result at code-unit offset 10.

Reading both assembled Alias classes with the ordinary get-class command confirms that reverse-and-XOR moves from a to b and bitCount-plus-five moves from b to a. Both short names, owners and prototypes still exist in both inputs, yet following each unchanged name leads to the other operation. Pool indexes and declaration order do not resolve this conflict.

The candidate comparison paired the two Alias bodies across their swapped names and paired Gate by its original full signature and instruction evidence. Gate's handler delta identifies the old protected range [0x4,0x7), handler at 0x8, and the new range [0xa,0xd), handler at 0xe. These boundaries contain the original array read and division. A separate fragment result relates five instructions starting at 0 in the old Kernel and new Gate, ending with move-result. The helper remains visible as a former standalone definition. This agrees with the authored movement and catch change.
